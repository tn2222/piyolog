# GrafanaとMac通知のデータ源をぴよログ公開フィードへ分離する

- **Date**: 2026-09-16
- **Status**: Accepted

## Context

<!-- 要監修: 議論から作成した本文。背景と制約が意図に合っているか確認する。 -->

GrafanaとMacのミルク通知は、テキストエクスポート由来の `piyolog_events` を参照している。取り込みは5分ごとに更新ファイルを確認し、テキストに含まれる日付のイベントをDELETEして再登録する。対象外の日付は残るため、履歴も蓄積される。

公開されたぴよログのデータフィードには、これらの用途で必要なミルクの日時・量、排泄などのイベントが含まれる。一方、LLMのサマリーに必要な各記録のメモ・メモ記録・日記は含まれないため、既存のテキスト・日記取り込みを引き続き必要とする。

APIのデータを既存テーブルへ混在させると、テキスト取り込みの日単位置換と競合する。また、フィードの取得範囲は暦日ではなく生成時刻を基準とした直近の期間なので、従来の日単位DELETEを流用すると取得範囲外の記録を消してしまう。

## Decision

<!-- 要監修: 議論から作成した本文。選択と理由が意図に合っているか確認する。 -->

GrafanaとMac通知のデータ源を公開フィードへ切り替え、API由来のイベントを専用テーブル `piyolog_feed_events` に保存する。LLMは既存の `piyolog_events` と `piyolog_diaries` を参照し続ける。既存テーブルへの統合よりも、取り込み処理同士の干渉を避け、LLM用のメモと日記を維持することを優先する。

既存のCloudflare Workerから5分ごとにフィードを取得する。正常なレスポンスを検証した後、`range.from <= 記録日時 < range.to` の既存行をDELETEし、取得レコードを `event_id` をキーにUPSERTする。日時変更によって同じIDが範囲外に残っている場合も更新できるよう、単純なINSERTにはしない。DELETEとUPSERTは1トランザクションで実行する。

範囲外の履歴は残し、取得できた分から蓄積する。既存データは移行しない。正常な空配列は取得範囲内を削除し、取得・検証・DB更新の失敗時は既存データを保持する。

## Consequences

### Positive

- GrafanaとMac通知は、テキストエクスポートの更新を待たずに公開フィードからイベントを取得できる。
- LLM用のメモ・日記と既存の取り込み処理を維持できる。
- 取得範囲内の追加・編集・削除を反映しながら、過去の履歴を蓄積できる。

### Negative

- APIとテキストの2経路を維持するため、同じイベントが別テーブルに保存され、更新のタイミングによって内容に差が生じる。
- 取得範囲外の編集・削除には完全に追従できない。取得が24時間を超えて途絶えた場合、24時間フィードだけでは欠損期間を埋められない。

### Neutral

- 新テーブルの履歴は初回取得範囲から始まる。既存テーブルの過去データはLLM用に残る。
- APIの日時はUTCなので、Grafanaの日別集計とMac通知の計算・表示はタイムゾーンを合わせる必要がある。

## Notes

- フィードURLは認証情報としてSecretで管理する。
- 初回同期を確認してからGrafanaとMac通知の参照先を切り替える。現時点では実装前。
